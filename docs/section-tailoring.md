# Section-by-section AI tailoring (v0.42)

The previous browser flow asked for resume and cover-letter wording together,
with up to twenty fact edits inside one 4096-token response. The observed
RW-AI-OUTPUT-LIMIT means that structured response did not finish. It does not
identify whether visible output or internal model reasoning used the budget.

## Use the smaller workflow

1. Open a saved opportunity and choose **Tailor with AI**.
2. Choose **Headline and summary**, **Experience or project wording**, or
   **Cover-letter wording**. Start with the summary using relevant source facts.
3. Review the request, enter the request-only key and send. Review and accept the
   wording you want. RoleWeave saves an application draft and opens the builder.
4. Choose **Tailor this resume with AI** in that builder to continue from the saved
   application. For experience, choose one entry first, then repeat for another.
5. Preview the complete document locally, adjust its selected entries and save
   the PDF. No model is needed for document layout or PDF assembly.

Each pass creates an immutable application version. Previously accepted summary,
experience and letter wording carry forward when continuing from the builder.
Reopen the latest **Open draft** from the Application kit after restarting.
Starting from the job's **Tailor with AI** action starts from the master profile.
Unaccepted edits and unsaved layout choices are not transferred to another pass.
The initial section draft selects up to twenty reviewed profile facts for local
assembly; review this selection in the builder. These are not all sent to AI.

## Request bounds

| Task | Selected source facts | Model output |
| --- | --- | --- |
| Headline and summary | Up to 6 | Headline up to 120 characters; summary up to 600 |
| Experience/project wording | Up to 3; one selected initially | Up to 3 fact edits, each up to 700 characters |
| Cover-letter wording | Up to 6 | Introduction up to 900 characters; closing up to 300 |
| Compact assessment | Up to 6 | Up to 6 key exact quotes, with reasons up to 250 characters |

Each task permits up to three brief questions. Source claims are bounded to
12000 characters and the supplied content to 48000 characters per compact request.
The 4096-token response cap remains unchanged. Scope and length are constrained
in both the JSON schema and response validation. Unrelated draft fields are
filled with empty placeholders locally, rather than generated by the model.
Empty or incomplete responses never become accepted wording.

Compact assessments cover selected key requirements, not full posting coverage.
They use a separate comparison rubric from old broad assessments. Original saved
assessments and refinement conversations still load under their original formats;
new section history and compact assessment records use version 2. Retained section
history also keeps the local application selection and letter context for reopening.

## Failure and provider limits

A failed pass leaves earlier saved application versions available. Review a new
request or reduce the section's sources. There are no automatic retries or paid
fallbacks. Every request still requires review, a fresh request-only credential
and send consent. Free model availability, structured-output support, latency and
reasoning behavior can still prevent completion; smaller tasks are not a guarantee
of provider success. Reasoning settings are not blindly disabled on router models.

Verification uses synthetic provider envelopes, isolated browser practice and
recovery tests. No personal API key or resume is sent by the test suite. Live
account acceptance and the quality of generated wording need a real reviewed trial.


## v0.42.1: About-only sources and empty responses

A real request contained a blank `claim` with substantive responsibilities in
`entry_context.about`. The previous instruction could be read as excluding that
source, while the output schema legitimately permitted an empty result. The app
then displayed a blank acceptance editor. The supplied screenshot does not prove
why the model chose no wording or establish that its job-specific expertise matched.

Scoped requests now explicitly permit rephrasing reviewed responsibilities already
present in About text. Titles, employers, dates and skills alone still do not imply
achievements. Transferable experience must not be presented as unsupported
job-specific experience. When claim text is blank and About text is present, source
review shows the About text and accepting experience edits replaces that text in the
application variant. It is not appended as a duplicate claim. Legacy unscoped edits
retain their existing behavior.

A completed response without any wording shows **No wording proposed**, any model
questions, and the original request/proposal for inspection. It offers source changes,
a fresh reviewed request and history, with no accuracy checkbox or acceptance button.
Empty responses remain valid historical records and cannot be accepted as edits.
Nothing is automatically retried and no provider call is needed to reopen a record.

## v0.47 section compatibility

Headline/summary requests allow a 120-character headline and 1200-character summary.
The parser accepts the full established draft envelope only when every unused
section is exactly empty; it never adopts unrelated wording. Source checks remain
strict. Shape, source-reference and length failures have separate static codes.
Prompts keep entry headings and source IDs out of printable experience wording.
No live provider request was used to verify these changes.
